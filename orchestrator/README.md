# Orchestrator

**Local pipeline**: `python3 orchestrator/run_pipeline.py [--offline] [--modules m1,m2,m3,m4] [--out OUT] [--event-dir DIR] [--event-tag TAG]` chains M1 enrich -> M2 comms -> M3 repurpose -> M4 dashboard (`seed`->`sync`->`analyze`->`render`) via subprocess. **Live by default** -- every stage calls its real backend (HubSpot, Clay, OpenRouter, Sarvam) unless `--offline` replays fixtures instead, zero network. `--modules` runs a subset in order (e.g. `--modules m1,m4` to skip M2/M3, useful for a fixture with no transcript). Prints a stage/seconds/key-output/pass-fail receipt table, exits nonzero on any stage failure. Also: `--gen-visuals`/`--live-visuals` (M3 image generation), `--no-publish` (skip the Drive-publish stage), `--transcribe-live` (real Sarvam STT instead of a dry run) -- see `--help` for the full flag list. `watch_folder.sh` re-runs it automatically whenever `data/incoming/registrants.csv` changes (fswatch if installed, else a 10s mtime poll).

**n8n: one JSON set, `n8n/railway/`.**

Four workflow exports, one per module -- `m1-lead-enrichment.json`, `m2-post-event-comms.json`, `m3-content-repurposing.json`, `m4-lead-intelligence.json`. They target self-hosted n8n on Railway and call the module API (`api/server.py`) for every HubSpot/Clay/OpenRouter/Sarvam/Drive step, with a Wait-node approval gate on M2. `n8n/railway/README.md` has the import steps, env vars, and the trigger for each workflow.

**None of the four has been imported into a running n8n instance** (same statement as `docs/architecture.md`'s "How it runs today"). What ships is the exports plus a static check of them -- see the "Audit result" sections in `n8n/railway/README.md`, which state what was and was not verified. For a walkthrough with no n8n at all, `python3 orchestrator/run_pipeline.py --offline --out out/replay` runs the same DAG locally.
