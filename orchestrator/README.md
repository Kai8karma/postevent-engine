# Orchestrator

**Local demo lane**: `python3 orchestrator/run_pipeline.py [--live] [--out out/pipeline]` chains M1 enrich -> M2 comms -> M3 repurpose -> M4 dashboard via subprocess, offline by default (`--live` switches to real LLM calls). Prints a stage/seconds/key-output/pass-fail receipt table, exits nonzero on any stage failure. `watch_folder.sh` re-runs it automatically whenever `data/incoming/registrants.csv` changes (fswatch if installed, else a 10s mtime poll).

**n8n: two lanes, honestly labeled.**

- `n8n/local-demo/` -- same DAG as Execute Command nodes shelling to the CLI scripts (what was previously just `n8n/*.json`). Every workflow's name is suffixed `[LOCAL DEMO STAND-IN]` and carries a Sticky Note explaining that Execute Command is self-hosted-only and this is NOT the production design. `master.json` is the full pipeline (4 Execute Command nodes -> approval-gate IF -> HubSpot-send stub -> a disabled-by-default Telegram notify stub); `m1-enrichment.json`, `m2-comms.json`, `m3-repurpose.json`, `m4-dashboard.json` mirror each module standalone.
- `n8n/cloud/master.json` -- the real production workflow, importable on n8n Cloud as-is: `webhook` trigger (`POST /webinar-ended`) -> `httpRequest` fetch registrants (webinar platform, credential placeholder) -> `httpRequest` push to Clay table (webhook-URL source) -> `wait` (resume-on-webhook Clay enrichment callback -- Clay enrichment is async, so this pauses until Clay posts the enriched rows back; without it the next node would read `clay_*` fields before Clay wrote them) -> `code` node shaping the payload to the M1 contract -> two `httpRequest` nodes for HubSpot CRM v3 batch upsert (contacts, companies) -> `httpRequest` v4 batch association -> `wait` (resume-on-webhook human approval gate) -> `if` approved check -> `httpRequest` HubSpot Single-Send -> `telegram` notify (`disabled: true`). All four credential slots are placeholders (`PLACEHOLDER_*`) to be wired to a real HubSpot private app / webinar platform / Telegram bot before running.

To import either lane: run n8n locally with no account needed — `docker run -it --rm -p 5678:5678 n8nio/n8n` (preferred; `npx n8n` fails on machines where Python 3.12+ breaks node-gyp's isolated-vm build, e.g. this one) — open http://localhost:5678, then Workflows -> Import from File -> pick any JSON in `orchestrator/n8n/local-demo/` or `orchestrator/n8n/cloud/`. Local-demo Execute Command nodes assume `cwd` = repo root. JSON schema/node-type correctness was verified by inspection against n8n's current node catalog and `python3 -c "import json; json.load(...)"` on every file. The local-demo lane (`orchestrator/n8n/local-demo/`) has not been interactively imported into a running n8n instance -- do that before a live judge demo if possible. The cloud lane (`orchestrator/n8n/cloud/master.json`) *was* interactively imported into a live n8n Cloud instance via UI Import-from-File (account `agentkai`, workflow id `rxJnu5ZATDFLJToD`, 13 nodes, verified present in the DOM and saved) per the 2026-08-23 build record -- that claim has not been independently re-verified by a fresh auditor since, and the workflow has never been executed end to end (the HubSpot leg still needs a credential the reviewer supplies).
