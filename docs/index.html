What the free model taught the code, all fixed in this build and kept: reasoning-style models (we tried stealth/ox-alpha first) wrap JSON in fences and append a sentence after the closing fence, spend their whole completion budget thinking on a long transcript, and take ~2 min a call — so every module now extracts the first complete JSON value rather than trusting the whole response, sizes timeouts/max_tokens for it, retries a non-JSON answer, validates the shape against the renderer's contract before persisting anything, and OPENROUTER_MODEL accepts a comma-separated fallback chain for when a free provider is overloaded (it was, twice).

M1 — spec completeness, measured against the brief's own field list

The brief asks for "contact and company completeness above 90 percent." Most completeness numbers quietly include easy fields (email, first/last name) that inflate the average — this one doesn't. spec_completeness() in modules/m1-enrichment/enrich.py scores only the fields the brief actually names, prints the result to M1's stdout, and stores it under quality_report.json → spec_completeness.

Both clear the 90% bar, but two honest caveats travel with that number, not around it: company completeness is measured per contact-row, not deduped to unique company objects (deduping first would hide exactly the rows whose company never resolved — the weak spot this metric exists to surface); and the size-band field is a synthetic offline placeholder never checked against a real source, so it reads as ~100% filled by construction, not by data quality. Both caveats are printed alongside the numbers in quality_report.json, not hidden in this page.

Honesty: lanes, depth, and what a fingerprint proves

The two lanes this build runs, and how deep the AI actually goes in each module — read before the architecture diagrams below assume you already know the difference.

Run it yourself: live console app — postevent-engine.vercel.app (this write-up lives at /control-room). Offline, zero keys, ~1s: python3 orchestrator/run_pipeline.py. Live, real LLM calls: LLM_BACKEND=openrouter OPENROUTER_MODEL="nvidia/nemotron-3.5-lightning:free,nvidia/nemotron-3-super-120b-a12b:free,nvidia/nemotron-3-ultra-550b-a55b:free" python3 orchestrator/run_pipeline.py --live. Clone: git clone https://github.com/Kai8karma/postevent-engine && cd postevent-engine
Thesis: AI does the actual reasoning work in this build, but not identically across modules, and we'd rather show you the real shape of that than round it up. M1 runs a deterministic rules lane offline (dedupe + field inference by lookup table, zero LLM tokens) and switches to real LLM classification with --live; M2 and M3 ship genuinely LLM-generated copy, replayed from a fingerprint-guarded cache offline so the demo doesn't need an API key; M4 computes its metrics directly from data and calls a live LLM only for the narrative summary, falling back to a labeled cached one without a key. Humans approve every send either way.

Anomaly/scoring rules stay deterministic in both lanes by choice: auditable, reproducible, and the LLM reads their output rather than inventing it.
What the fingerprint proves, and what it doesn't: compute_fingerprint() in modules/m2-comms/comms.py hashes exactly two things — the transcript's SHA-256 and the event name — and the offline lane refuses to silently replay a cached sample whose fingerprint doesn't match what's on record (the “frankenstein guard”). That proves one thing only: the cached copy in sample_output/ was generated from this transcript and this event, not a stale one swapped in later. It does not prove a model authored that copy — authorship is only provable by actually running --live and reading the receipt (see Live receipts), which is why every honesty claim in this build points back to a receipt, not to the fingerprint alone.

Depth, ranked honestly

The brief says attempt all four, depth of execution matters more than breadth — all four were attempted; what was missing was saying out loud which is deepest and why. In order:

RankModuleWhy
1M1 EnrichmentReal dedupe math (a stated weighted composite score, not a black box — data contract §2), a live Clay enrichment run and a live HubSpot sandbox push (not a dry-run), and completeness measured against the brief's own named fields, not an inflated denominator (99.8% contact / 97.2% company, both above the 90% bar — scorecard).
2M3 RepurposingA real extraction-to-asset chain — one claude -p extraction pass over the transcript, then every asset (blog/YouTube/infographic/social) generated off that extraction rather than each guessing independently off the raw transcript (modules/m3-repurpose/repurpose.py) — and a grounding verifier (modules/m3-repurpose/verify_grounding.py) that checks every timestamp, quote, and speaker attribution each asset claims against the source transcript, fuzzy-matching quotes with the same primitive M1's dedupe uses, and writes a per-asset pass/fail grounding_report.json.
3M2 CommsStrong content generation and real CRM send-log wiring, deliberately stopped short of an actual send — the human approval gate (approval_gate.json, never auto-flipped) is a design choice, not an unfinished feature.
4M4 DashboardBest engineering, thinnest AI — by choice. One live narrative call; anomaly detection and lead-interest scoring are deterministic rules, not LLM calls. Reproducibility is a compliance property here, not a missed opportunity: an SDR disputing a merge a year from now needs a byte-identical replay of how that account got scored, and a deterministic rule gives them that where a model call wouldn't.
