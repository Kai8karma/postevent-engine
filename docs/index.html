Post-Event Engine — one real Darwinbox webinar, four modules

AI is the engine

Every “AI role” cell in the brief is a real model call with a receipt, not a template with slots. The reasoning steps, module by module — each one named, each one logged to receipts/*_llm_calls.json with model, purpose, prompt size, latency, HTTP status and parse result.

M1 — four reasoning jobs, each checked by the rule engine

  • Gray-zone dedupe adjudication. Pairs scoring in [0.65, 0.80) are too ambiguous for a fixed threshold, so the model sees both records and rules same-person or not — capped at 20 pairs per run, every decision written to dedupe_report.json.gray_zone_adjudication. In the committed slice the band caught exactly one pair, within-batch, and the model ruled no merge with a written rationale; the live HubSpot-side search logged matches: 0, gray_zone_pairs: 0, so no CRM-side pair reached the model in that run.
  • Row inference. Title, function and seniority for the contacts the rule cascade could not resolve (modules/m1-enrichment/prompts/inference.md).
  • Firmographic inference. Industry from config/icp.yaml's own vocabulary, plus an employee-count estimate and a confidence, batched once per distinct company. Clay values overwrite the model's when they arrive; each field carries industry_source / numemployees_source (clay|llm|rules|synthetic).
  • ICP tier + rationale. The model scores; icp_tier() recomputes the same tier deterministically. A model tier more than one level away still ships but sets needs_review_reason=icp_disagreement for a human to adjudicate. That is the capability, not the committed receipt's result: two ICP batches timed out against the free model's 90-second per-batch deadline, which retired that model for the run, so the third was never attempted, so icp_rows_scored_by_llm: 0, icp_rows_rules_fallback: 32 and source_mix.icp_source: {rules: 32} — every tier in that slice is the rule table's, recorded as such rather than passed off as model output.

M2 — one extraction, three segment writes, one grounding gate

  • Extraction is the only call that sees the transcript: takeaways with [MM:SS] anchors, verbatim quotes with speaker and timestamp, the moments worth a no-show's click, and a personalisation matrix — one angle per CRM function, one follow-on sentence per industry bucket.
  • Three segment calls (attendee / no-show / speaker) each see only that extraction and return two subjects, a preheader, a body template and takeaways. The speaker mail carries a performance snapshot computed from M1 plus the attendance segments.
  • Grounding verifier. Every quoted span and every timestamp in the extraction, the variants and the rendered bodies is re-matched against the transcript. A miss fails the run before a dispatch plan exists — 81 of 81 checks passed on the committed run.

M3 — extraction → per-asset generation → hard grounding gate

  • Extraction pass returns clip-worthy moments, insights, verbatim quotes and data points; normalise_extraction() snaps every timestamp onto a real transcript turn, replaces each speaker with whoever the transcript shows at that timestamp, and drops anything that does not verify — so asset prompts never see ungrounded material.
  • Four asset generations (blog, YouTube pack, infographic outline, social set) run off that verified extraction. Each is checked by check_asset_spec() before it is written; the blog's 800–1200 word gate regenerates once and fails the run rather than shipping out of spec.
  • Grounding verifier re-checks every timestamp, quote ≥25 characters and speaker attribution after generation; a failing asset gets one corrective regeneration, and the run fails if it still misses. 46 of 46 claims verified on the committed run — youtube.md 18, infographic.md 12, social.md 9, blog.md 7. An earlier version of this receipt read 39/39 because the verifier matched speakers by surname only, so prose like “As Q explained” attributed nothing and every blog quote was skipped; after fixing that and adding elided-quote support, re-running the shipped verifier over the same committed assets gives 46/46. Reproduce: python3 modules/m3-repurpose/verify_grounding.py --transcript data/incoming/transcript.md --event data/incoming/event.json --assets-dir out/receipts/m3-live
  • Clips and captions are deterministic: the model picks the moments, ffmpeg cuts them, and the captions come from Sarvam's own word timings.

M4 — four analyses over the portal snapshot, graded by the maths

  • Anomalies — the model judges the outlier fence's shortlist (accept, reject with a reason, or add one it missed), each with the evidence rows behind it.
  • Lead-interest scores — 0–100 per contact with a short rationale and its evidence, plus the model's own top five for the validator to compare.
  • Stage-movement narrative — what moved across 7 / 14 / 30 days, what did not, and where the movement is seeded rather than organic.
  • Buying committees — which multi-contact accounts are real committees, and why.
Deterministic maths validates the model; it never silently replaces it. The Tukey (Q3 + 1.5×IQR) outlier fence, the weighted engagement score, the funnel and the 7/14/30-day movement windows compute the same quantities independently. Every mismatch is written to analysis.json.llm.validator.disagreements and printed on the dashboard — the committed portal run records 4 agreements and 3 disagreements, and nothing the model returned overwrote a number. Where a model call fails, the module says so: M1 degrades that batch to the rule table with a warning and a lane reason, M2 and M3 fail the run rather than ship stale copy. No module presents a rules output as a model output.

Real vs simulated

Stated once, plainly, so nothing on this page has to be taken on trust.

REAL

What is real

The event, its public page, its recording and both speakers. The transcript — a real Sarvam batch STT run over the real chapter audio. Every generated artifact (blog, chapters, infographic, social posts, email copy, dedupe adjudications, ICP rationales, dashboard analysis) is the output of a real model call with a per-call receipt. The HubSpot dedupe searches, the contact/company/association writes, the property and lifecycle updates and the portal read-back are real API calls against a HubSpot developer test portal.

GENERATED

What is generated or simulated

The registrant list. 150 rows from data/incoming/tools/gen_registrants.py: employer companies, domains, roles and regions are real so enrichment returns real firmographics, but every registrant's name and email address is invented. No shareable attendee list exists for this webinar, so none was used.

M4's engagement stream. Opens, clicks, page views, form fills and lifecycle changes did not happen on their own — dashboard.py seed writes them into a HubSpot developer test portal through the public API and everything from it is labelled source: "seeded" in the seed receipt, on every snapshot engagement block, in each movement window's source_mix and on the dashboard badge.

Images: 0 of 3 shipped. Every attempt returned HTTP 402 on an unfunded key. The receipt records the model, the status and the error; no placeholder image was written in their place.

The model lane runs mostly, not entirely, on free-tier OpenRouter models. M1, M3 and M4's committed runs used nvidia/nemotron-3-super-120b-a12b:free and its fallback chain, which is why some calls show provider 502/429 retries. M2's committed run did not — all four calls ran on google/gemini-2.5-flash-lite, a paid model, for roughly half a US cent.

Two smaller disclosures, both in data/incoming/event.json._provenance: the event page publishes no air date, so event.json.date is an assumption every downstream artifact inherits; and the speakers' own addresses are not public, so speaker mail is addressed to sender-controlled aliases. The 30-day window holds 40 lifecycle transitions, dated {"2026-09-13": 1, "2026-09-21": 39}. The 39 on 2026-09-21 were written by this pipeline that afternoon — 32 by the M1 push, 7 by the seed phase. The 40th is older: the Q Hamirani speaker contact moving to lead at 2026-09-13T11:05:41, before either step ran. The dashboard card and the narrative both disclose the seeding — the narrative's opening sentence attributes the burst to the pipeline's seed phase and its source-mix paragraph gives the 7 / 32 split — rather than letting HubSpot's property history read as weeks of organic movement. The narrative is model-written, so a re-run rewords it; the disclosure is enforced, not its wording.

Orchestration

n8n owns the triggers, the waits, the approval gate, the sends and the Drive leg. It calls the modules over HTTP through one small stdlib service (api/server.py), one module or phase per POST /run — so the reviewer watches an execution, not a shell script. The workflows below are in the repo and audited; none has been imported into a running instance yet.

Run it

The live lane is the default in every module. The replay lane is an explicit flag for a reviewer with no keys — it replays this repo's own checked-in output and refuses to run if the cache came from a different transcript or event (SHA-256 fingerprint check), so a replay can never be another webinar's output.

Live lane (default)

python3 orchestrator/run_pipeline.py --out out/live

Needs OPENROUTER_API_KEY and HUBSPOT_TOKEN in the environment or ~/.config/postevent/*.env; SARVAM_API_KEY for M3's transcription phase. M3's clips also need ffmpeg and ffprobe on PATH plus Pillow. Clips and images are live-only and are never replayed.

Replay lane (no keys, zero network)

python3 orchestrator/run_pipeline.py --offline --out out/replay open out/replay/m4/index.html

Through the module API, the way n8n calls it

curl -s -X POST "$MODULE_API_URL/run" \ -H "Authorization: Bearer $MODULE_API_TOKEN" \ -H 'Content-Type: application/json' \ -d '{"module":"m1","live":true,"inputs":{"registrants_csv_path":"data/incoming/registrants.csv"}}'
To point this at a different event: replace the four files in data/incoming/ (event.json, speakers.json, registrants.csv, the recording), regenerate transcript.md with the transcription phase, and adjust config/icp.yaml if the buyer profile changes. M3 and M4 also accept an event_slug that resolves to data/events/<slug>/ and fails loud rather than falling back to the bundled fixture.
